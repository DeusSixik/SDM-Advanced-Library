# Автоматические сетевые пакеты

Пакет — публичный `record` или обычный класс, который реализует `Packet` и имеет
`@NetworkPacket(id = "mymod:example", side = Side.SERVER)`.
`Side` обозначает **сторону получения**: `SERVER` — C2S, `CLIENT` — S2C.
Ручная регистрация пакетов и сгенерированные Java-классы не нужны.

```java
import dev.sixik.sdmal.api.network.Packet;
import dev.sixik.sdmal.api.network.PacketContext;
import dev.sixik.sdmal.api.network.Side;
import dev.sixik.sdmal.api.network.annotations.NetworkPacket;
import net.minecraft.network.chat.Component;

@NetworkPacket(id = "mymod:ping", side = Side.SERVER)
public record PingPacket(long nonce) implements Packet {
    @Override
    public void handle(PacketContext context) {
        context.reply(new PongPacket(nonce));
    }
}
```

В другом файле:

```java
@NetworkPacket(id = "mymod:pong", side = Side.CLIENT)
public record PongPacket(long nonce) implements Packet {
    @Override
    public void handle(PacketContext context) {
        context.player().sendSystemMessage(Component.literal("Pong: " + nonce));
    }
}
```

Отправка:

```java
new PingPacket(42L).send();                  // из игрового клиента на сервер
new PongPacket(42L).send(serverPlayer);      // с сервера одному игроку
new PongPacket(42L).send(minecraftServer);   // всем игрокам сервера во всех измерениях
new PongPacket(42L).send(new Player[]{first, second});
new PongPacket(42L).send(players);           // Collection<? extends Player>, включая List<ServerPlayer>
```

Неверное направление вызывает исключение. Отправлять можно после установки
игрового соединения. При использовании из worker-потока защищайте изменяемые данные
пакета на время `send`: сериализация синхронно снимает копию перед передачей транспорту.

Рассылка доступна для `Side.CLIENT`. Она проверяет всех получателей до начала
отправки и кодирует пакет **один раз** для всей группы. `null` и клиентские
экземпляры `Player` отклоняются; повторяющиеся получатели получают пакет повторно.
Пустая группа проверяет регистрацию и направление, но не сериализует пакет.
Получатели и данные должны оставаться стабильными на время вызова. `send(MinecraftServer)`
вызывайте в серверном игровом потоке: он использует текущий список подключённых игроков.

## Поля и пользовательские типы

Все поля экземпляра сериализуются автоматически, включая унаследованные поля и
поля с приватным доступом. `static`, `transient` и синтетические поля исключаются.
Для обычного класса нужен конструктор без аргументов (допускается приватный);
передаваемые поля должны быть изменяемыми. Для неизменяемого пакета используйте
`record`: декодер вызывает его канонический конструктор. Конструкторы должны только
создавать данные; проверка прав и изменение мира относятся к `handle`.

`@EcsSync` на пакете необязателен и задаёт стабильное имя поля:

```java
public record ExamplePacket(@EcsSync("energy") long storedEnergy) implements Packet {
    // ...
}
```

Ключ выбирается в порядке `@EcsSync("key")`, `@EcsPersist("key")`, имя Java-поля.
Порядок объявления полей не влияет на формат; ключи сортируются. Без явного ключа
переименование поля меняет схему. Разные поля не могут иметь один ключ.
В ECS-компонентах правила прежние: передаются только выбранные `@EcsSync` поля.

Форматы переиспользуют `EcsNetworkSerializers`: примитивы, строки, UUID, поддержанные
типы Minecraft (например, `BlockPos`), массивы, enum, `List<T>`, `Map<K,V>`,
`Optional<T>`, вложенные `@EcsData` records. Для вложенного `@EcsData` сохраняются
правила ECS: у его полей должны быть стабильные ключи `@EcsSync` / `@EcsPersist`.
Ссылочные поля могут содержать `null`. Необработанные generic-типы, циклические схемы
и произвольные классы без адаптера не поддерживаются.

```java
EcsNetworkSerializers.register(MyValue.class, new MyValueNetworkSerializer());
```

Адаптер реализует `EcsNetworkSerializer<MyValue>`: `schemaName()`,
`write(FriendlyByteBuf, MyValue)`, `read(FriendlyByteBuf)`. Можно назначить отдельный
адаптер полю через `@EcsUseNetworkAdapter`. NBT-сериализатор не требуется и при
передаче не вызывается. Зарегистрируйте адаптер до первой отправки/приёма такого
пакета; успешная схема кешируется. При изменении бинарного формата адаптера меняйте
его `schemaName`.

## Контекст и поток выполнения

`handle` и декодирование выполняются в игровом потоке получателя. `context` предоставляет:

- `side()` — логическую сторону получения;
- `player()` — отправителя на сервере или локального игрока на клиенте;
- `sender()` — авторизованного `ServerPlayer`, только для C2S;
- `level()` — текущий мир этого игрока;
- `reply(packet)` — ответ через то же соединение;
- `enqueueWork(runnable)` — дополнительную работу в игровом executor.

Личность отправителя определяется соединением. C2S обработчик обязан проверять
права, дистанцию, координаты, размер/смысл данных и возможность операции.
В `example/network/RequestGeneratorStatusPacket` показаны проверка дистанции
до 8 блоков, отсутствие принудительной загрузки чанков и ответ состоянием ECS.
`GeneratorStatusPacket` показывает S2C и стабильный ключ `@EcsSync`.

## Автоматическая регистрация в другом моде

В этом репозитории processor подключён всем основным source sets. В потребляющем моде
добавьте JAR `sdmal-ecs-processor` в `annotationProcessor` **каждого модуля, который
компилирует классы пакетов**, и обычную зависимость на SDMAL. Например, для локального
JAR processor:

```groovy
dependencies {
    annotationProcessor files('libs/sdmal-ecs-processor-1.0.0.jar')
}
```

Этот же JAR содержит processor ECS-компонентов. Processor выполняется только при
компиляции; устанавливать его в `mods` не требуется. При упаковке/объединении JAR
сохраняйте и объединяйте строки ресурсов `META-INF/sdmal/network-packets`.
Не перемещайте автоматически индексируемый пакет в source set только для клиента:
его объявление должно присутствовать и на сервере; клиентские классы используйте
из отдельного helper, вызываемого только в CLIENT `handle`.

При запуске библиотека читает индексы всех модов, проверяет уникальность id и
регистрирует транспорт Fabric/Forge/NeoForge. Пакеты не создаются при обнаружении;
схемы строятся при первом использовании. Если индекс отсутствует, `send` сообщает
о необходимости подключить processor. Изменения не требуют перегенерации Java-исходников в IDEA.

## Формат и ограничения

Один игровой канал `sdmal:packets` переносит версию протокола, строковый id,
64-битный fingerprint схемы и поля непосредственно в `FriendlyByteBuf`.
Порядок загрузки модов не меняет id пакетов. Поддерживаются игровые C2S/S2C пакеты;
login/configuration, разбиение больших сообщений и согласование версий
модовых схем не входят в этот API.

Максимальный логический кадр — **30 КиБ** в обоих направлениях, включая id и
fingerprint. Это укладывается в ограничения старого C2S транспорта. Для больших
данных нужен отдельный протокол порций. Неизвестный id, несовпадение схемы,
повреждённые данные, неверная сторона и лишние байты отклоняются до `handle`;
получатель закрывает несовместимое соединение. Ошибки самого обработчика пишутся
в лог. Работа, ожидающая игровой executor, отбрасывается после отключения.

Это проверка совместимости и формата, а не авторизация игровых действий.
Обе стороны должны иметь совместимые схемы используемых пакетов.

## Проверка производительности

```powershell
./gradlew.bat :core:1.20.1:jmhPackets
```

Изолированный `PacketBenchmark` сравнивает полный автоматический кадр с ручным
бинарным форматом тех же байтов: encode/decode, 5 прогревов + 5 измерений,
1 fork, GC profiler. Результат сохраняется в
`core/versions/1.20.1/build/reports/jmh/packets.json`.
Сетевой RTT и TPS этим измерением не проверяются.

Локальное измерение на Java 17 (1.20.1), один небольшой пакет с `long`, `int` и
строкой; среднее ± погрешность JMH:

| Операция | Автоматически, нс/op | Вручную, нс/op | Автоматически, B/op | Вручную, B/op |
| --- | ---: | ---: | ---: | ---: |
| Encode полного кадра | 57.52 ± 2.65 | 39.68 ± 3.53 | 480 | 440 |
| Decode полного кадра | 71.16 ± 1.20 | 33.51 ± 2.17 | 272 | 152 |

Автоматический путь здесь медленнее ручного и выделяет больше памяти:
декодирование record требует массива аргументов конструктора и boxing примитивов.
Эти цифры характеризуют данный workload и машину; это не обещание общей
производительности и не zero-allocation API.

Для сравнения групповой отправки с циклом отдельных `send(player)`:

```powershell
./gradlew.bat :core:1.20.1:jmhPacketBroadcast
```

`PacketBroadcastBenchmark` вызывает реальные перегрузки `Packet.send` с массивом
и коллекцией из 1 или 32 записей получателей. Входные данные создаются до замера;
transport принимает общий кадр без сетевого I/O. Получатели — непрозрачные тестовые
`ServerPlayer`; метрики относятся к сериализации и маршрутизации одного вызова рассылки,
а не к доставке сообщений по сети. Настройки: 5 прогревов + 5 измерений, 1 fork,
GC profiler. JSON сохраняется в
`core/versions/1.20.1/build/reports/jmh/packet-broadcast.json`.

Локальный результат на Java 17 / 1.20.1, среднее ± погрешность JMH за один вызов:

| Отправка | Получателей | нс/op | B/op |
| --- | ---: | ---: | ---: |
| `send(Player[])` | 1 | 66.10 ± 31.93 | 456 |
| `send(Collection)` | 1 | 55.76 ± 0.98 | 456 |
| Цикл `send(player)` | 1 | 55.96 ± 0.59 | 456 |
| `send(Player[])` | 32 | 334.81 ± 5.63 | 456 |
| `send(Collection)` | 32 | 309.42 ± 4.43 | 456 |
| Цикл `send(player)` | 32 | 1803.53 ± 136.96 | 14592 |

Для группы из 32 записей один общий логический кадр сократил аллокации этой части
отправки в 32 раза. Для одного получателя преимущества не подтверждены; замер
массива с одним получателем имеет большую погрешность. Нативная упаковка кадра
и сетевые буферы загрузчика для каждого соединения в эти цифры не входят.
