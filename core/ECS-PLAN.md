# План развития ECS

Этап 1 реализован. Проверки перечислены в ECS.md.

1. Один владелец-менеджер у WorldObject; очистка при закрытии, отключении и замене мира.
2. Менеджер принадлежит потоку создания. Прямые структурные изменения управляемых
   объектов выполняются в этом потоке; остальные потоки используют ограниченную
   очередь команд. Отложенная работа имеет бюджет на один тик.
3. Порядок обхода объектов фиксируется порядком регистрации. Сон и интервал тика
   позволяют исключать неактивную работу; исходное поведение — тик каждый раз.
4. Замороженные схемы полей кешируются. Запросы по классам и типам компонентов
   возвращают снимки в порядке регистрации, включая спящие объекты.
5. Ошибки отдельных компонентов не прерывают остальных; повторные сообщения об
   ошибках ограничиваются, фатальные ошибки JVM не подавляются.
6. JUnit на каждый контракт, проверка Minecraft-хуков на пяти версиях,
   JMH для схем и тиков, полная сборка 14 вариантов загрузчиков.

## Этап 2: сохранение мира — реализован

1. Версионированный NBT-архив: UUID, порядок компонентов, настройки тиков, данные.
2. Контракт persistent-компонента и миграции его схемы до прикрепления к объекту.
3. Неизвестные/несовместимые объекты сохраняются целиком и не тикают.
4. Снимок на потоке мира, отдельный файл на серверное измерение, временный файл,
   резервная копия и запрет перезаписи после неудачной загрузки.
5. Хуки загрузки, ванильного сохранения и закрытия; тесты на всех пяти версиях.
6. Копия на потоковом файловом вводе ограничена по compressed size и NBT budget;
   checksum gzip проверяется перед признанием архива загруженным.
7. Запись временного архива, проверка до замены, `.bak`, восстановление после
   повреждения и блокировка перезаписи неизвестного будущего формата.
8. Регрессионные тесты проверяют миграции, reentrant callbacks, opaque-объекты,
   отказы сериализаторов и сохранность прежнего файла при ошибках.

## Дополнение: декларативное сохранение — реализовано

1. Обычные private/унаследованные поля через `@EcsPersist` и отдельный
   `AnnotatedWorldObjectComponent`, без изменения API существующих компонентов.
2. Records с `@EcsData`, точные generic-типы и nullable-значения.
3. Реестр NBT-only адаптеров и `@EcsUseAdapter` для формата отдельного поля.
4. Проверка схемы при регистрации, кешированные средства доступа и ошибки с путём поля.
5. Интеграция с версиями/миграциями и сохранением неизвестного объекта;
   JUnit на всех пяти версиях и сборка 14 вариантов загрузчиков.
6. Независимый выбор сетевых полей через `@EcsSync`, прямые binary-снимки
   `FriendlyByteBuf`, сетевые адаптеры и контроль совместимости схем без NBT.
7. Атомарное применение прочитанного снимка, ограниченные размеры,
   откат индексов буфера при ошибке; отдельные JUnit и сравнительный JMH.
8. `@EcsComponent` и generated registration index: компонент регистрируется
   по стабильному ID без ручного дескриптора и без runtime classpath scan.

Протокол сетевой репликации, архетипы/SoA и планировщик систем остаются следующими этапами.
